# Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения

**Мониторинг температуры:**

- Пользователи могут удаленно получать информацию о температуре в своих домах
- Система поддерживает получение данных с датчиков о температуре в домах пользователей

### 2. Анализ архитектуры монолитного приложения

- Язык программирования - Golang
- База данных - PostgreSQL
- Архитектура приложения - монолитная
- Взаимодействие между компонентами - синхронное, обработка запросов последовательно
- Масштабируемость - ограниченная
- Развертываемость - ограниченная, обновление приложения требует перезапуска всего приложения

### 3. Определение доменов и границы контекстов

Ниже перечислены домены, реализованные в текущем монолите.

**1. Управление устройствами**

- Поддомены:
    - Реестр датчиков — создание, чтение, изменение и удаление датчиков
    - Метаданные и размещение — имя, тип, дом
    - Состояние устройства — текущее значение и статус датчика
- Ограниченный контекст: управление устройствами

**2. Мониторинг температуры** 

- Поддомены:
    - Приём показаний — получение текущей температуры от внешнего источника
    - Выдача показаний — передача текущего значения пользователю
- Ограниченный контекст: телеметрия

Не хватает доменов управления отоплением, домами и пользователями.

### **4. Проблемы монолитного решения**

Классические проблемы монолита
- Сложная развертываемость - ограниченная, обновление приложения требует перезапуска всего приложения
- Сложная масштабируемость - придется поднимать копию приложения целиком, а не только нагруженную часть
- Сложная разработка в команде - большой риск пересечений кода, мерджи, конфликты, потеря кода
- Сложное добавление новых функций - придется переписывать весь код, чтобы добавить новую функциональность
- Сложно писать тесты - сложно покрыть весь код тестами
- Сложно вводить человека в проект - большой и сложный код на входе
- и тд

На уровне текущего приложения, при минимальном использовании, необходимости в микросервисах нет.
Необходимость в них появляется
- При добавлении нового функционала, который не связан с температурой. При появлении в перспективе больше одного дополнительного функционала. Тоесть минимум 3-4 не связанных между собой блоков.
- При росте потребителей, когда растет нагрузка на систему. Если стоимость закупа оборудования и возможность его масштабирования станет проблемой. Это если оставаться на монолите с большим количеством функций.
- При повышении сложности и частой модификации кода. Включая увеличение различных функциональных блоков.
- Можно еще добавить сравнение стоимости поддержания монолита (или монолитов) против стоимости переписывания на микросервисы и их поддержки.

В настоящий момент проект не сложный, функционал один фактически, достичь предела железа будет сложно объемами. Микросервисы дороже на старте и здесь смысла не имеют.

# Задание 4. Создание и документирование API

### 1. Тип API

В системе три контура взаимодействия, и у каждого свой тип описания.

**Внешний контур — REST/JSON поверх HTTPS, документируется OpenAPI.** Мобильное приложение и админка обращаются к платформе только через API Gateway. Swagger позволяет идти и от контракта к реализации, и в обратную сторону, что удобно в большой команде и при постоянных правках.

**Внутренний контур между микросервисами — тоже REST, документируется OpenAPI.** Рассматривал gRPC и отклонил. Шлюз при gRPC внутри вынужден разбирать тело запроса и знать контракт каждого сервиса, то есть превращается в точку связности со всеми одиннадцатью, при REST он пробрасывает запрос, не заглядывая внутрь. Синхронных вызовов между сервисами мало — почти всё общение идёт событиями, — поэтому выигрыш gRPC в скорости не окупает поддержку второго контракта на каждый сервис.

**Асинхронный контур — RabbitMQ и канал до домашнего хаба, документируется AsyncAPI.**

Критерий разделения простой: **синхронно то, где нужен ответ, асинхронно то, что является свершившимся фактом.** Команда устройству требует ответа — выполнилась или нет, поэтому это синхронный REST. Измерение или смена состояния ответа не требуют: это сообщение о том, что уже произошло.

Через AsyncAPI описываются:

| Сообщение | Кто публикует → кто потребляет | Почему асинхронно |
|---|---|---|
| `MeasurementReceived` | Device Control → Telemetry, Automation | наибольший поток в системе, потребителей несколько, потеря единичного значения терпима; приём данных от домов не должен останавливаться из-за недоступности потребителя |
| `DeviceRegistered`, `DeviceUpdated`, `DeviceDecommissioned` | Device Registry → Telemetry, Automation | на них строятся локальные проекции; синхронный вызов реестра на пути приёма измерений дал бы N+1 и связал доступность сервисов |
| `ReferenceChanged` | Reference Data → Device Registry | справочник читают все; синхронное обращение к нему на каждый запрос превратило бы его в общую базу для всей системы, то есть в распределённый монолит |
| `CommandCompleted`, `DeviceStateChanged` | Device Control → Notification | результат команды — факт, ответ на него не нужен |
| `ScenarioTriggered` | Automation → Notification | сценарий не должен ждать, пока доставится push |
| `RecordingStored` | Video → Notification | факт появления записи в архиве |

Отдельно AsyncAPI описывает **канал до домашнего хаба**: при активной сессии приложения он поднимается в WebSocket и становится двунаправленным. OpenAPI такой обмен описать не может в принципе — он рассчитан на модель «запрос и ответ». Длинный опрос за командами при этом остаётся обычным HTTP и описан в OpenAPI Device Control.

Надёжность публикации обеспечивается паттерном Outbox: событие пишется в базу одной транзакцией с изменением данных и отправляется отдельным процессом. Исключение — поток измерений: он публикуется напрямую, потому что объём наибольший, а потеря единичного значения допустима.

### 2. Документация API

Спецификации собраны для трёх микросервисов, для которых сделаны диаграммы уровня кода.

**Синхронный контур — OpenAPI 3.0:**

- [События платформы](schemas/api/asyncapi-events.yaml) — обмен через RabbitMQ и двунаправленный канал до хаба

# Задание 5. Работа с docker и docker-compose

**[temperature-api](apps/temperature-api)** — Java 17, Spring Boot 3.2, одна зависимость `spring-boot-starter-web`. Порт 8081.

| Метод | Кто вызывает |
|---|---|
| `GET /temperature?location=&sensor_id=` | `GetTemperature` монолита и проверка из задания |
| `GET /temperature/{sensorId}` | `GetTemperatureByID` монолита при выдаче списка датчиков |
| `GET /health` | проверка руками |

Оба метода отдают одно и то же тело — поля совпадают со структурой `TemperatureResponse` в [temperature_service.go](apps/smart_home/services/temperature_service.go), включая `sensor_id` и `sensor_type` через подчёркивание. Значение случайное в диапазоне 18–26 °C с двумя знаками после запятой.

# **Задание 6. Разработка MVP**

**[device-registry](apps/device-registry)** — Java 17, Spring Boot 3.2, порт 8082. **[telemetry-service](apps/telemetry-service)** — Python 3.12, FastAPI, порт 8083. У каждого своя PostgreSQL.

| Метод | Что отдаёт |
|---|---|
| `GET /api/v1/devices` | реестр датчиков, `include_deleted=true` вернёт и удалённые |
| `GET /api/v1/devices/{id}` | карточка датчика |
| `GET /api/v1/measurements?device_id=&from=&to=` | ряд измерений |
| `GET /api/v1/measurements/latest?device_id=` | последнее измерение |

Запуск — надстройкой над compose задания 5, который при этом не меняется:

```
docker compose -f docker-compose.yml -f docker-compose.microservices.yml up -d --build
```

Оба сервиса раз в 10–15 секунд зовут `GET /api/v1/sensors` монолита. Реестр сверяет состав: новое заводит, исчезнувшее помечает `deleted_at`. Телеметрия пишет по строке на датчик — это история, которой у монолита нет вовсе: он перезаписывает значение в строке. Монолит не менялся и о микросервисах не знает, инициатива обмена целиком на их стороне.

**Это MVP, а не архитектура из заданий 2–4.** Сделан первый шаг вытеснения: рядом с монолитом строится параллельная копия данных. В целевой архитектуре обмен идёт событиями через RabbitMQ, Telemetry на Java, модель на UUID и возможностях устройства — здесь опрос по REST, Python. Диаграммы под MVP не правил: они описывают целевое состояние, к которому это только первый шаг.
