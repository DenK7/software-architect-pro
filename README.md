# Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения

**Мониторинг температуры:**

- Пользователи могут удаленно получать информацию о температуре в своих домах
- Система поддерживает получение данных с датчиков о температуре в домах пользователей

### 2. Анализ архитектуры монолитного приложения

- Язык программирования - Golang
- База данных - PostgreSQL
- Архитектура приложения - монолитная
- Взаимодействие между компонентами - синхронное, обработка запросов последовательно
- Масштабируемость - ограниченная
- Развертываемость - ограниченная, обновление приложения требует перезапуска всего приложения

### 3. Определение доменов и границы контекстов

Ниже перечислены домены, реализованные в текущем монолите.

**1. Управление устройствами**

- Поддомены:
    - Реестр датчиков — создание, чтение, изменение и удаление датчиков
    - Метаданные и размещение — имя, тип, дом
    - Состояние устройства — текущее значение и статус датчика
- Ограниченный контекст: управление устройствами

**2. Мониторинг температуры** 

- Поддомены:
    - Приём показаний — получение текущей температуры от внешнего источника
    - Выдача показаний — передача текущего значения пользователю
- Ограниченный контекст: телеметрия

Не хватает доменов управления отоплением, домами и пользователями.

### **4. Проблемы монолитного решения**

Классические проблемы монолита
- Сложная развертываемость - ограниченная, обновление приложения требует перезапуска всего приложения
- Сложная масштабируемость - придется поднимать копию приложения целиком, а не только нагруженную часть
- Сложная разработка в команде - большой риск пересечений кода, мерджи, конфликты, потеря кода
- Сложное добавление новых функций - придется переписывать весь код, чтобы добавить новую функциональность
- Сложно писать тесты - сложно покрыть весь код тестами
- Сложно вводить человека в проект - большой и сложный код на входе
- и тд

На уровне текущего приложения, при минимальном использовании, необходимости в микросервисах нет.
Необходимость в них появляется
- При добавлении нового функционала, который не связан с температурой. При появлении в перспективе больше одного дополнительного функционала. Тоесть минимум 3-4 не связанных между собой блоков.
- При росте потребителей, когда растет нагрузка на систему. Если стоимость закупа оборудования и возможность его масштабирования станет проблемой. Это если оставаться на монолите с большим количеством функций.
- При повышении сложности и частой модификации кода. Включая увеличение различных функциональных блоков.
- Можно еще добавить сравнение стоимости поддержания монолита (или монолитов) против стоимости переписывания на микросервисы и их поддержки.

В настоящий момент проект не сложный, функционал один фактически, достичь предела железа будет сложно объемами. Микросервисы дороже на старте и здесь смысла не имеют.

# Задание 5. Работа с docker и docker-compose

Перейдите в apps.

Там находится приложение-монолит для работы с датчиками температуры. В README.md описано как запустить решение.

Вам нужно:

1) сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```

2) Приложение следует упаковать в Docker и добавить в docker-compose. Порт по умолчанию должен быть 8081

3) Кроме того для smart_home приложения требуется база данных - добавьте в docker-compose файл настройки для запуска postgres с указанием скрипта инициализации ./smart_home/init.sql

Для проверки можно использовать Postman коллекцию smarthome-api.postman_collection.json и вызвать:

- Create Sensor
- Get All Sensors

Должно при каждом вызове отображаться разное значение температуры

Ревьюер будет проверять точно так же.
