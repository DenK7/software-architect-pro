## Владение хранилищами

| Сервис | Назначение | Хранилище |
|---|---|---|
| API Gateway | единая точка входа, проверка токена, ограничение частоты, аудит | Redis — счётчики частоты запросов |
| User Service | учётные записи, профили, роли, выдача токенов | PostgreSQL; внешний Vault — закрытый ключ подписи |
| Home Service | дома пользователя, привязка устройств к дому | PostgreSQL |
| Device Registry | реестр устройств: паспорт, возможности, онбординг и вывод из эксплуатации | PostgreSQL |
| Device Control | канал до хаба, доставка команд, желаемое и сообщённое состояние | PostgreSQL; Redis — реестр соединений, очереди команд, шина между репликами |
| Telemetry Service | приём измерений, временные ряды, выдача текущего значения и истории | PostgreSQL с расширением TimescaleDB |
| Video Service | метаданные записей, выдача подписанных ссылок, срок хранения | PostgreSQL — метаданные записей; MinIO — файлы |
| Automation Service | пользовательские сценарии «триггер → условие → действие» | PostgreSQL |
| Catalog Service | комплекты, заказы, активация серийных номеров | PostgreSQL; MinIO — изображения комплектов |
| Reference Data | типы устройств и возможностей, метрики, единицы, протоколы | PostgreSQL |
| Notification Service | оповещения пользователю через push и электронную почту | PostgreSQL; внешний Vault — ключ шифрования push-токенов |

Общей базы нет ни у кого: PostgreSQL на диаграмме — один контейнер СУБД, но внутри у каждого сервиса своя схема, к которой никто другой не обращается.

## Ключевые взаимодействия

**Весь трафик дома идёт в Device Control.** Один контур аутентификации по ключу устройства, но запросы внутри него разные. Хаб держит длинный опрос за командами, при открытом приложении вместо опроса поднимается WebSocket. Измерения уходят своим запросом пакетами — прицепить их к длинному опросу нельзя, иначе отправка данных привязалась бы к циклу ожидания команды.

**Измерения и события устройств публикуются по-разному.** Событие о смене состояния или регистрации проходит через outbox: потеря такого события навсегда рассинхронизирует проекции в других сервисах. Измерения — поток, где потеря единичного значения терпима, а объём наибольший в системе, поэтому Device Control публикует их в RabbitMQ напрямую, без записи в свою базу. Иначе самый горячий путь системы упирался бы в запись в PostgreSQL.

**Команды не привязаны к соединению.** Любая реплика Device Control принимает команду и кладёт её в очередь устройства в Redis, после чего уведомляет через Redis pub/sub ту реплику, что держит соединение с этим хабом. Sticky-маршрутизация не нужна, реплики добавляются свободно, а падение реплики теряет только сокеты: хабы переподключаются к любой другой и забирают накопленное из очереди. У команды есть срок годности — просроченная отбраковывается при выдаче, чтобы «включить свет в 22:00» не сработало в час ночи после долгого офлайна.

**Расписания считаются по времени дома.** Планировщик сценариев кластерный, с хранением расписаний в базе Automation: иначе каждая реплика отработала бы одно и то же расписание. Часовой пояс Automation получает у Home Service при создании сценария и хранит вместе с ним.

**Видеозаписи не проходят через прикладной сервис.** Хаб запрашивает у Video Service подписанную ссылку с коротким сроком жизни, заливает файл прямо в MinIO и сообщает об окончании. Просмотр устроен симметрично: приложение получает подписанную ссылку и скачивает запись из хранилища напрямую, минуя шлюз. Video Service владеет метаданными, правами и сроком хранения, но байтов не касается.

**Видеоаналитика живёт на краю системы.** Живой поток в облако не выходит, поэтому движение распознаёт камера или хаб. Событие идёт обычным путём устройства — через Device Control в RabbitMQ — и по капабилити-модели ничем не отличается от показаний датчика движения. Video Service публикует только факт сохранения записи, на который Notification может оповестить пользователя.

**Сценарии работают на событиях и целиком в облаке.** Automation подписан на измерения и события устройств, команду отдаёт синхронным вызовом в Device Control — команде нужен ответ, событие тут не подходит. О срабатывании сценария публикует событие, которое забирает Notification. Локального исполнения правил на хабе нет: при обрыве связи с облаком автоматика не работает, дом остаётся управляемым только вручную. Это осознанное ограничение текущего этапа.

**Полномочия администратора не выходят за учётные записи.** Он создаёт, изменяет и удаляет пользователей, назначает роли и ведёт справочники платформы. Доступа к домам, устройствам, телеметрии и записям пользователей у него нет, поэтому права нигде не пересекают границу арендатора и отдельный механизм доступа поддержки не требуется.

**Телеметрия не зависит от реестра.** Device Registry публикует события о регистрации, изменении и выводе устройств, Telemetry держит локальную проекцию — идентификатор, дом, набор метрик. Синхронных вызовов в реестр на пути приёма измерений нет: реестр может быть недоступен, поток данных от этого не прервётся.

**Справочники раздаются событиями.** Reference Data публикует изменения, потребители держат локальные копии. Синхронно в него на каждый запрос никто не ходит — иначе он станет общей базой для всех.

**Активация комплекта доводит устройства до реестра.** Catalog проверяет серийные номера купленного комплекта и регистрирует устройства в Device Registry, после чего они появляются у пользователя и ждут подключения через хаб.

**Токены выдаёт User Service, проверяет шлюз.** Подпись асимметричная, шлюз забирает открытый ключ у User Service и кэширует его. Общего секрета между сервисами нет, собственного хранилища учёток у шлюза тоже.

**Vault — внешняя система, а не наш сервис.** Это готовое приложение для хранения секретов и параметров конфигурации, живущее за границей платформы и обслуживающее её целиком. Каждый сервис при старте забирает оттуда свои настройки и учётные данные: строку подключения к базе, пароль к брокеру, ключи доступа к объектному хранилищу. На диаграмме эта связь показана одной стрелкой от границы облака — рисовать её от каждого из одиннадцати сервисов значило бы превратить схему в звезду.

**Настоящие секреты в базах не лежат.** Два из них выделены отдельными стрелками, потому что используются не при старте, а в работе: закрытый ключ подписи токенов у User Service и ключ шифрования push-токенов у Notification Service. User Service не держит ключ даже в памяти — он отправляет полезную нагрузку в Vault и получает подпись, а в своей базе хранит только метаданные ключа и открытую часть. Граница простая: если секретом можно воспользоваться — место в Vault, если им можно только проверить предъявленное, как хешем пароля, — место в базе рядом с данными.

**Общая библиотека разбора токена подключена во все сервисы.** Она умеет ровно две вещи: разобрать полезную нагрузку токена и проверить подпись, — и поднимает из неё контекст вызова: пользователь, роль, дом. Бизнес-логики и сетевых обращений в ней нет сознательно, иначе её обновление затрагивало бы все одиннадцать сервисов сразу. Отдельным контейнером на диаграмме она не показана, потому что не разворачивается самостоятельно: это зависимость внутри каждого сервиса.
