# ER-диаграмма

У каждого сервиса собственная база — общей схемы нет ни у кого. Поэтому диаграмма разбита на независимые блоки: по одному на сервис, владеющий данными в PostgreSQL. API Gateway в список не входит, у него только Redis со счётчиками частоты запросов.

**Связи между сервисами не являются внешними ключами.** Поля вроде `home_id` в реестре устройств или `user_id` в уведомлениях — это ссылки на сущности чужих баз, и целостность по ним обеспечивается не СУБД, а событиями и проверками при записи. Внутри одного блока внешние ключи настоящие.

**Удаление везде логическое.** Физического `DELETE` в бизнес-таблицах нет: запись помечается парой `deleted_at` и `deleted_by`, а данные остаются. Порядок колонок везде один: идентификаторы, затем поля фиксированной длины, затем переменной.

## 1. User Service

```mermaid
erDiagram
    USERS ||--o{ REFRESH_TOKENS : "выдаёт"
    USERS ||--o{ USER_AUDIT : "изменяется в"

    USERS["USERS — учётные записи и профили"] {
        uuid id PK "идентификатор учётной записи"
        uuid deleted_by "кто удалил, пусто пока запись жива"
        timestamptz created_at "момент регистрации"
        timestamptz updated_at "последнее изменение профиля"
        timestamptz deleted_at "момент логического удаления"
        user_status status "активна, заблокирована"
        user_role role "пользователь или администратор"
        varchar email UK "логин и канал связи"
        varchar password_hash "хеш пароля, сам пароль не хранится"
        varchar display_name "отображаемое имя"
    }
    REFRESH_TOKENS["REFRESH_TOKENS — токены обновления сессий"] {
        uuid id PK "идентификатор записи"
        uuid user_id FK "владелец токена"
        uuid deleted_by "кто отозвал токен"
        timestamptz issued_at "момент выдачи"
        timestamptz expires_at "срок действия"
        timestamptz deleted_at "момент отзыва, отзыв и есть удаление"
        varchar token_hash UK "хеш токена, сам токен не хранится"
    }
    SIGNING_KEYS["SIGNING_KEYS — метаданные ключей подписи"] {
        uuid id PK "идентификатор пары ключей"
        uuid deleted_by "кто вывел ключ из обращения"
        timestamptz created_at "момент генерации пары"
        timestamptz not_after "до какого момента ей подписывать"
        timestamptz deleted_at "момент вывода из обращения"
        boolean active "текущая пара для подписи"
        varchar kid UK "идентификатор ключа в заголовке токена"
        varchar algorithm "алгоритм подписи"
        varchar vault_key_path "путь к ключу во внешнем Vault, в базе ключа нет"
        text public_key "открытый ключ, его забирает шлюз"
    }
    USER_AUDIT["USER_AUDIT — журнал действий администратора"] {
        uuid id PK "идентификатор записи аудита"
        uuid actor_id FK "кто выполнил действие"
        uuid target_user_id "над чьей учётной записью"
        timestamptz occurred_at "момент действия"
        audit_action action "создание, изменение, блокировка, удаление"
        varchar details "что именно изменилось"
    }
```

`SIGNING_KEYS` хранит **метаданные** ключей подписи, но не сам закрытый ключ. Он лежит во внешнем Vault, и подпись выполняется там же: сервис отправляет полезную нагрузку и получает подпись, ключ не попадает даже в память приложения. В базе остаются `kid`, алгоритм, срок действия и открытый ключ — по `kid` из заголовка токена шлюз находит, каким ключом проверять подпись.

Держать закрытый ключ в той же базе, что и таблицу `USERS`, было бы опасно несоразмерно: владение им даёт выпуск токена от имени любого пользователя, включая администратора, причём беззвучно — подделанный токен неотличим от настоящего.

`USER_AUDIT` — единственная таблица здесь без логического удаления: журнал аудита не удаляется вовсе, иначе он теряет смысл. Именно в нём остаётся след того, кто и когда удалил учётную запись.

## 2. Home Service

```mermaid
erDiagram
    HOMES["HOMES — дома пользователей"] {
        uuid id PK "идентификатор дома"
        uuid owner_user_id "владелец, ссылка в User Service без внешнего ключа"
        uuid deleted_by "кто удалил дом"
        timestamptz created_at "момент создания"
        timestamptz updated_at "последнее изменение"
        timestamptz deleted_at "момент логического удаления"
        varchar timezone "часовой пояс дома, по нему считаются расписания"
        varchar name "название, заданное пользователем"
        varchar address "адрес дома"
    }
```

Одна таблица — и это честное отражение решений. Помещений нет: дом считается единым пространством. Совместного доступа нет: у дома один владелец, поэтому нет ни таблицы участников, ни таблицы прав.

`timezone` здесь не декоративное поле: по нему Automation считает расписания, иначе «в 22:00» срабатывало бы по времени сервера.

## 3. Device Registry

```mermaid
erDiagram
    DEVICE_TYPE_PROJECTION ||--o{ CAPABILITY_PROJECTION : "описывается"
    DEVICE_TYPE_PROJECTION ||--o{ DEVICES : "воплощается в"

    DEVICES["DEVICES — реестр устройств пользователей"] {
        uuid id PK "идентификатор устройства"
        uuid type_id FK "тип из проекции справочника"
        uuid home_id "дом, ссылка в Home Service без внешнего ключа"
        uuid owner_user_id "владелец, ссылка в User Service"
        uuid deleted_by "кто вывел устройство из эксплуатации"
        timestamptz registered_at "момент постановки на учёт"
        timestamptz last_seen_at "последняя активность, по ней переводится в офлайн"
        timestamptz deleted_at "момент логического удаления"
        device_status status "зарегистрировано, активно, офлайн, выведено"
        varchar serial_number UK "серийный номер с коробки"
        varchar name "имя, заданное пользователем"
    }
    DEVICE_TYPE_PROJECTION["DEVICE_TYPE_PROJECTION — локальная копия типов устройств"] {
        uuid id PK "идентификатор типа, совпадает со справочником"
        timestamptz updated_at "когда проекция обновлена событием"
        boolean active "тип доступен к подключению"
        varchar code UK "код типа"
        varchar manufacturer "производитель"
        varchar model "модель"
    }
    CAPABILITY_PROJECTION["CAPABILITY_PROJECTION — локальная копия возможностей"] {
        uuid id PK "идентификатор возможности"
        uuid type_id FK "к какому типу относится"
        numeric min_value "нижняя граница допустимого значения"
        numeric max_value "верхняя граница допустимого значения"
        boolean read_only "возможность только на чтение"
        capability_kind kind "включение, уровень, уставка, замок, датчик, поток"
        varchar metric_code "какая метрика, для возможностей вида датчик"
        varchar unit_code "единица измерения"
    }
    OUTBOX["OUTBOX — исходящие события сервиса"] {
        uuid id PK "идентификатор события"
        uuid aggregate_id "к какой записи относится событие"
        timestamptz occurred_at "момент возникновения"
        timestamptz published_at "момент отправки, пусто пока не отправлено"
        varchar type "тип события"
        jsonb payload "тело события"
    }
```

Две таблицы с суффиксом `PROJECTION` — локальная копия справочника, обновляемая событиями Reference Data. Логического удаления у них нет намеренно: это зеркало чужих данных, оно восстанавливается из событий и живёт ровно столько, сколько живёт оригинал.

`home_id` ссылается в чужую базу без внешнего ключа: существование дома подтверждается вызовом Home Lookup API при регистрации, дальше связь поддерживается событиями.

## 4. Device Control

```mermaid
erDiagram
    DEVICE_SHADOW ||--o{ COMMANDS : "меняется командами"

    COMMANDS["COMMANDS — история команд устройствам"] {
        uuid id PK "идентификатор команды, возвращается клиенту"
        uuid device_id FK "адресат команды"
        uuid issued_by_user_id "кто отдал, пусто если команда от сценария"
        timestamptz created_at "момент приёма"
        timestamptz expires_at "до какого момента команда актуальна"
        timestamptz sent_at "когда выдана хабу"
        timestamptz completed_at "когда подтверждена или отбракована"
        smallint attempts "число попыток доставки, ограничивает повторы"
        command_status status "проверка, в очереди, отправлена, выполнена, ошибка, просрочена"
        capability_kind capability "над какой возможностью устройства"
        varchar action "действие внутри возможности"
        varchar failure_reason "причина отказа устройства"
        jsonb params "параметры, у разных возможностей различны"
    }
    DEVICE_SHADOW["DEVICE_SHADOW — желаемое и сообщённое состояние"] {
        uuid device_id PK "устройство, одна запись на устройство"
        timestamptz desired_at "когда задано желаемое состояние"
        timestamptz reported_at "когда устройство отчиталось"
        boolean online "есть ли связь с хабом сейчас"
        jsonb desired "каким состояние должно быть"
        jsonb reported "каким устройство его сообщило"
    }
    HUB_CREDENTIALS["HUB_CREDENTIALS — ключи домашних хабов"] {
        uuid id PK "идентификатор записи"
        uuid hub_id UK "идентификатор хаба"
        uuid home_id "дом, в котором стоит хаб"
        uuid deleted_by "кто отозвал ключ"
        timestamptz created_at "момент выдачи ключа"
        timestamptz rotated_at "последняя смена ключа"
        timestamptz deleted_at "момент отзыва, отзыв и есть удаление"
        varchar key_hash "хеш ключа, сам ключ не хранится"
    }
    OUTBOX["OUTBOX — исходящие события сервиса"] {
        uuid id PK "идентификатор события"
        uuid aggregate_id "к какой записи относится событие"
        timestamptz occurred_at "момент возникновения"
        timestamptz published_at "момент отправки, пусто пока не отправлено"
        varchar type "тип события"
        jsonb payload "тело события"
    }
```

Очереди команд и реестр соединений здесь отсутствуют намеренно — они живут в Redis, потому что это короткоживущее состояние с высокой частотой обращений. В PostgreSQL остаётся история команд, по которой можно ответить, что именно происходило с устройством.

`expires_at` и `attempts` — та самая пара, что реализует срок годности и ограничение повторов из диаграммы жизненного цикла команды.

`COMMANDS` и `DEVICE_SHADOW` логического удаления не имеют: история команд не удаляется пользователем, а теневое состояние живёт ровно столько, сколько живёт устройство.

`params` хранится как JSONB осознанно: у команд разных возможностей параметры принципиально разные, и раскладывать их по колонкам пришлось бы заново при каждом новом типе устройства. Это ровно тот случай, который отличается от значений измерений, где JSONB отвергнут.

## 5. Telemetry Service

```mermaid
erDiagram
    DEVICE_PROJECTION ||--o{ DEVICE_METRIC_PROJECTION : "отдаёт метрики"
    DEVICE_PROJECTION ||--o{ MEASUREMENTS : "порождает"

    MEASUREMENTS["MEASUREMENTS — временные ряды измерений"] {
        uuid device_id PK "источник измерения"
        timestamptz ts PK "момент измерения, ключ разбиения гипертаблицы"
        numeric value_numeric "числовое значение, для температуры и подобных"
        boolean value_bool "булево значение, для датчиков движения"
        measurement_quality quality "норма, устаревшее, ошибка"
        varchar metric_code PK "что именно измерено"
        varchar unit_code "в чём измерено"
        varchar value_text "текстовое состояние, для открыто и закрыто"
    }
    DEVICE_PROJECTION["DEVICE_PROJECTION — локальная копия устройств"] {
        uuid device_id PK "устройство из реестра"
        uuid home_id "дом, по нему фильтруются выборки"
        timestamptz updated_at "когда проекция обновлена событием"
        device_status status "состояние, полученное из реестра"
    }
    DEVICE_METRIC_PROJECTION["DEVICE_METRIC_PROJECTION — метрики, доступные устройству"] {
        uuid device_id PK "устройство"
        varchar metric_code PK "метрика, допустимая для этого устройства"
        varchar unit_code "единица измерения по умолчанию"
    }
    RETENTION_RULES["RETENTION_RULES — правила срока хранения"] {
        uuid id PK "идентификатор правила"
        uuid deleted_by "кто удалил правило"
        timestamptz deleted_at "момент логического удаления"
        smallint keep_raw_days "сколько дней хранить сырые измерения"
        smallint keep_rollup_days "сколько дней хранить агрегаты"
        varchar metric_code UK "для какой метрики правило"
    }
```

`MEASUREMENTS` — гипертаблица TimescaleDB с разбиением по времени. Ключ составной: устройство, метрика и момент времени. Именно метрика в ключе позволяет комбинированному датчику отдавать температуру и влажность одновременно — в монолите это было невозможно, там один датчик равнялся одному значению.

Три колонки значения вместо одного универсального поля: `value_numeric`, `value_bool` и `value_text`. Датчик движения отдаёт булево, геркон — текстовое состояние, термометр — число. JSONB здесь отвергнут сознательно: по числовым рядам считаются агрегаты, и извлекать их из JSON на каждом запросе заметно дороже.

Логического удаления у измерений нет и быть не может: это миллиарды строк, которые удаляются политикой хранения целыми разделами. Пометка каждой строки удалённой лишила бы разбиение по времени всякого смысла.

## 6. Video Service

```mermaid
erDiagram
    QUOTA_USAGE ||--o{ RECORDINGS : "учитывает"

    RECORDINGS["RECORDINGS — метаданные видеозаписей"] {
        uuid id PK "идентификатор записи"
        uuid device_id "камера, с которой снято"
        uuid home_id FK "дом, для проверки доступа и квоты"
        uuid deleted_by "кто удалил запись"
        timestamptz started_at "начало фрагмента"
        timestamptz ended_at "конец фрагмента"
        timestamptz created_at "момент регистрации в сервисе"
        timestamptz deleted_at "момент логического удаления"
        bigint size_bytes "размер файла, списывается с квоты"
        integer duration_seconds "длительность фрагмента"
        recording_status status "ожидается, сохранена"
        varchar object_key UK "путь к объекту в MinIO"
        varchar content_type "формат файла"
    }
    QUOTA_USAGE["QUOTA_USAGE — расход квоты архива по домам"] {
        uuid home_id PK "дом, одна запись на дом"
        timestamptz updated_at "момент последнего пересчёта"
        bigint used_bytes "сколько занято архивом"
        bigint limit_bytes "предел по тарифу"
    }
    RETENTION_RULES["RETENTION_RULES — правила срока хранения"] {
        uuid id PK "идентификатор правила"
        uuid home_id "для какого дома действует"
        uuid deleted_by "кто удалил правило"
        timestamptz deleted_at "момент логического удаления"
        smallint keep_days "срок хранения записей в днях"
    }
    OUTBOX["OUTBOX — исходящие события сервиса"] {
        uuid id PK "идентификатор события"
        uuid aggregate_id "к какой записи относится событие"
        timestamptz occurred_at "момент возникновения"
        timestamptz published_at "момент отправки, пусто пока не отправлено"
        varchar type "тип события"
        jsonb payload "тело события"
    }
```

Файлов записей в базе нет — только `object_key`, путь к объекту в MinIO. Сам файл идёт от хаба в хранилище и обратно в приложение по подписанным ссылкам, минуя сервис.

Здесь логическое удаление работает в два такта и это стоит оговорить: запись помечается удалённой сразу, а файл из MinIO уходит отложенно, по истечении срока хранения. Пока файл на месте, удаление обратимо — пользователь может передумать.

## 7. Automation Service

```mermaid
erDiagram
    SCENARIOS ||--o{ TRIGGERS : "запускается по"
    SCENARIOS ||--o{ CONDITIONS : "ограничен"
    SCENARIOS ||--o{ ACTIONS : "выполняет"
    SCENARIOS ||--o{ EXECUTIONS : "срабатывает"

    SCENARIOS["SCENARIOS — пользовательские сценарии"] {
        uuid id PK "идентификатор сценария"
        uuid home_id "дом, к которому относится"
        uuid owner_user_id "автор сценария"
        uuid deleted_by "кто удалил сценарий"
        timestamptz created_at "момент создания"
        timestamptz updated_at "последнее изменение"
        timestamptz deleted_at "момент логического удаления"
        boolean enabled "включён ли сценарий"
        varchar timezone "копия часового пояса дома для расписаний"
        varchar name "название, заданное пользователем"
    }
    TRIGGERS["TRIGGERS — условия запуска сценария"] {
        uuid id PK "идентификатор триггера"
        uuid scenario_id FK "к какому сценарию относится"
        uuid device_id "источник события, пусто для расписания"
        uuid deleted_by "кто удалил триггер"
        timestamptz deleted_at "момент логического удаления"
        numeric threshold "порог срабатывания"
        trigger_kind kind "измерение, смена состояния, расписание"
        varchar metric_code "метрика, для триггера по измерению"
        varchar operator "сравнение: больше, меньше, равно"
        varchar cron_expression "расписание, для триггера по времени"
    }
    CONDITIONS["CONDITIONS — дополнительные проверки сценария"] {
        uuid id PK "идентификатор условия"
        uuid scenario_id FK "к какому сценарию относится"
        uuid device_id "чьё состояние проверяется"
        uuid deleted_by "кто удалил условие"
        timestamptz deleted_at "момент логического удаления"
        numeric value_numeric "числовое значение для сравнения"
        condition_kind kind "время суток, состояние устройства, порог"
        varchar metric_code "какая метрика проверяется"
        varchar operator "сравнение"
        varchar value_text "текстовое значение для сравнения"
    }
    ACTIONS["ACTIONS — действия сценария"] {
        uuid id PK "идентификатор действия"
        uuid scenario_id FK "к какому сценарию относится"
        uuid device_id "кому адресовано действие"
        uuid deleted_by "кто удалил действие"
        timestamptz deleted_at "момент логического удаления"
        smallint order_no "порядок выполнения внутри сценария"
        capability_kind capability "над какой возможностью"
        varchar action "действие внутри возможности"
        jsonb params "параметры действия"
    }
    EXECUTIONS["EXECUTIONS — журнал срабатываний"] {
        uuid id PK "идентификатор срабатывания"
        uuid scenario_id FK "какой сценарий сработал"
        timestamptz triggered_at "момент срабатывания"
        timestamptz finished_at "момент завершения"
```

`timezone` дублируется из Home Service намеренно: он копируется в сценарий при создании, чтобы планировщик не ходил за ним на каждое срабатывание. Плата за это — необходимость пересчитать сценарии дома при смене его часового пояса.

Удаление сценария помечает удалёнными и его триггеры, условия и действия — каскад тоже логический. Благодаря этому журнал `EXECUTIONS` остаётся читаемым: по нему видно, какой именно сценарий сработал, даже если пользователь давно его удалил. Сам журнал логического удаления не имеет и чистится по сроку хранения.

К этим таблицам добавляются служебные таблицы Quartz для хранения расписаний и блокировок — они создаются самой библиотекой и на диаграмме не показаны.

## Сквозные решения

**Удаление везде логическое.** Пара `deleted_at` и `deleted_by` есть во всех бизнес-таблицах. Физического `DELETE` нет: удалённая учётная запись сохраняет свои дома, устройства и историю, и остаётся ответ на вопрос, кто и когда её удалил. Из этого следуют три обязательных правила реализации:

- каждый запрос на чтение фильтрует по `deleted_at IS NULL`, иначе удалённое начнёт всплывать в выборках;
- уникальные индексы становятся частичными, с тем же условием — иначе освободившийся адрес электронной почты или серийный номер нельзя будет использовать повторно;
- каскад удаления тоже логический: удаление сценария помечает его триггеры, условия и действия, а не стирает их.

**Где логического удаления нет и почему.** `MEASUREMENTS` — миллиарды строк, удаляются политикой хранения целыми разделами. `OUTBOX` и `DEDUP_KEYS` — технические записи, исчезающие после отправки или по таймеру. `USER_AUDIT` и `EXECUTIONS` — журналы: первый не удаляется вовсе, второй чистится по сроку хранения. `COMMANDS`, `DEVICE_SHADOW`, `QUOTA_USAGE` и четыре таблицы-проекции — производное состояние, живущее ровно столько, сколько живёт его источник. `REFERENCE_VERSION` — счётчик версий, который только растёт.

**Флаг доступности и дата удаления — разные вещи.** `active` и `enabled` означают «выключено сейчас, можно включить обратно»: комплект снят с витрины, сценарий приостановлен, тип устройства временно недоступен. `deleted_at` означает «убрано насовсем, но данные сохранены ради целостности истории». Смешивать их нельзя — иначе нельзя будет отличить приостановленный сценарий от удалённого.

**Настоящие секреты в базах не лежат.** Их два, и оба во внешнем Vault — готовом приложении для хранения секретов и параметров конфигурации, откуда все сервисы забирают и свои настройки: закрытый ключ подписи токенов у User Service и ключ шифрования push-токенов у Notification Service. В базе от первого остаются метаданные и открытый ключ, от второго — зашифрованное значение. Граница проходит по признаку «можно ли этим воспользоваться»: если да — место в Vault, если только проверить предъявленное, как хешем пароля, — место в базе.

**Хеши вместо секретов.** Пароли, токены обновления и ключи хабов хранятся только как `password_hash`, `token_hash`, `key_hash`. Это не секреты, а верификаторы: предъявить их нельзя, ими можно только проверить предъявленное. Выносить их в Vault было бы неправильно и технически — это данные с реляционным жизненным циклом, привязанные к строкам, которых миллионы.

**Идентификаторы везде `uuid`, а не последовательности.** Устройства приходят от партнёров и регистрируются с разных сторон, так что идентификатор должен порождаться без обращения к общей базе. Это же избавляет от угадывания чужих записей перебором.

**Перечисления вынесены в типы PostgreSQL** (`device_status`, `command_status`, `capability_kind` и прочие), а не хранятся строками: база сама не даст записать несуществующее состояние.
